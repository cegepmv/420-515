Docker Compose : orchestrer plusieurs conteneurs

Plus tôt cette semaine, nous avons construit et exécuté un seul conteneur (docker build, docker run). Cette page prolonge ce travail : comment gérer une application qui a besoin de plusieurs conteneurs en même temps (l’API, une base de données, etc.) ?

1️⃣ Le problème que Compose résout

Documentation officielle de Docker :

« Avec Docker Compose, vous utilisez un fichier de configuration YAML […] pour configurer les services de votre application, puis vous créez et démarrez tous les services à partir de votre configuration avec la CLI Compose. » — Docker, How Compose works

Sans Compose, faire fonctionner ensemble une API et sa base de données exige de lancer manuellement plusieurs commandes docker run, dans le bon ordre, avec les bonnes options réseau et les bonnes variables d’environnement pour chacune. Compose remplace cette suite de commandes par un seul fichier déclaratif et une seule commande.

2️⃣ Anatomie d’un fichier Compose

Selon la documentation officielle, un fichier Compose décrit l’application sous forme de services :

« Les composants informatiques d’une application sont définis comme des services. Un service est un concept abstrait implémenté sur les plateformes en exécutant la même image de conteneur, et la même configuration, une ou plusieurs fois. » — Docker, How Compose works

Voici un exemple réel, tiré du docker-compose.yml du projet utilisé dans ce cours :

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.multistage
    ports:
      - "9966:9966"
    environment:
      - SPRING_PROFILES_ACTIVE=h2,spring-data-jpa

  mysql:
    image: mysql:8.4
    ports:
      - "3306:3306"
    environment:
      - MYSQL_ROOT_PASSWORD=
      - MYSQL_DATABASE=petclinic
    profiles:
      - mysql
Clé Rôle
services: Liste des conteneurs qui composent l’application (ici : app et mysql)
build: Construit l’image à partir d’un Dockerfile local, plutôt que de tirer une image déjà publiée (comme image:)
ports: Même syntaxe HOTE:CONTENEUR que docker run -p, vue plus tôt cette semaine
environment: Équivalent de docker run -e, vu plus tôt cette semaine
profiles: Permet de ne démarrer un service que lorsqu’il est explicitement demandé (ex. mysql ne démarre pas par défaut)

💡 Dans le fichier complet du projet, le service mysql monte aussi un volume (volumes: - "./conf.d:/etc/mysql/conf.d:ro") — le même concept de volume que celui vu dans Docker, pour conserver ou injecter des données en dehors du cycle de vie du conteneur.

3️⃣ Commandes de base

Commande Effet
docker compose up --build Construit les images si nécessaire, puis démarre tous les services définis (sans profiles)
docker compose up -d Démarre en arrière-plan, comme docker run -d vu plus tôt cette semaine
docker compose --profile mysql up -d Démarre aussi le service mysql (profil activé explicitement)
docker compose down Arrête et retire les conteneurs créés par up

4️⃣ Docker Compose et GitHub Actions : deux mécanismes complémentaires

GitHub Actions propose son propre mécanisme natif, indépendant de Compose, pour faire tourner des conteneurs de service pendant un job :

« Vous pouvez configurer des conteneurs de service pour chaque job d’un workflow […] par exemple, votre workflow pourrait avoir besoin d’exécuter des tests d’intégration qui nécessitent l’accès à une base de données et à un cache mémoire. » — GitHub Docs, Communicating with Docker service containers

Ce mécanisme utilise le mot-clé services: directement dans le YAML du workflow (pas un fichier Compose) :

jobs:
  test-integration:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.4
        ports:
          - 3306:3306

C’est l’approche recommandée par GitHub pour des besoins simples (une base de données pour les tests d’intégration, par exemple) — elle ne demande aucun fichier supplémentaire.

Cela dit, si votre application possède déjà un docker-compose.yml que vous utilisez en local (comme celui du projet du cours), rien n’empêche de réutiliser ce même fichier dans un workflow : les images des runners hébergés par GitHub incluent Docker Compose préinstallé —

« Docker Compose 2.38.2 » — actions/runner-images, Ubuntu 24.04 — Installed Software

— ce qui permet d’ajouter simplement une étape run: docker compose up -d dans le workflow, sans installation additionnelle.

Besoin Approche suggérée
Un ou deux services annexes (BD, cache) pour des tests d’intégration en CI services: natif de GitHub Actions
Reproduire en CI exactement la même pile multi-conteneurs qu’en local docker compose up -d (déjà préinstallé sur les runners hébergés)

5️⃣ Exemple de workflow : tests d’intégration avec docker compose

Comme pour le job de publication GHCR vu dans Registres de conteneurs, voici un job complet et autonome, cette fois pour démarrer la pile du projet (docker-compose.yml) et vérifier qu’elle répond, avant de l’arrêter proprement :

# .github/workflows/integration-test.yml
name: Integration Test (Docker Compose)

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  integration-test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v5

      - name: Démarrer la pile avec Docker Compose
        run: docker compose up --build -d

      - name: Attendre que l'application réponde
        run: |
          for i in $(seq 1 30); do
            if curl -sf http://localhost:9966/petclinic/api/owners; then
              exit 0
            fi
            sleep 2
          done
          echo "L'application n'a jamais répondu à temps" && exit 1

      - name: Afficher les journaux en cas d'échec
        if: failure()
        run: docker compose logs

      - name: Arrêter et nettoyer la pile
        if: always()
        run: docker compose down
Étape Rôle
docker compose up --build -d Construit (si nécessaire) et démarre tous les conteneurs du docker-compose.yml, en arrière-plan
Boucle curl Interroge un endpoint réel du projet (/petclinic/api/owners, le contexte et le port configurés dans application.properties) jusqu’à obtenir une réponse, ou échoue après 30 tentatives
docker compose logs N’affiche les journaux de tous les services que si une étape précédente a échoué (if: failure()) — utile pour diagnostiquer sans encombrer les exécutions réussies
docker compose down S’exécute toujours (if: always()), même en cas d’échec, pour éviter de laisser des conteneurs actifs sur le runner

« always provoque l’exécution systématique de l’étape, et retourne true, même en cas d’annulation. » — GitHub Docs, Evaluate expressions in workflows and actions

C’est ce qui garantit ici que docker compose down s’exécute systématiquement, même si l’étape d’attente précédente échoue.
