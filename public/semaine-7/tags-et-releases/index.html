Stratégie de tags et publications GitHub (Releases)

Une fois la publication d’image automatisée (voir Registres de conteneurs), reste à décider comment nommer les versions publiées et comment en garder une trace lisible par des humains — deux aspects de la traçabilité d’une version précise du projet.

1️⃣ Stratégie de tags : pourquoi (au moins) deux tags

Publier seulement latest rend impossible de savoir, plus tard, quelle version exacte du code correspond à l’image actuellement déployée. Publier systématiquement le SHA du commit en plus de latest garantit une traçabilité complète :

Tag Usage
ghcr.io/.../mon-projet:latest Pratique pour un docker pull rapide de « la dernière version » — mais son contenu change à chaque publication
ghcr.io/.../mon-projet:<sha-du-commit> Immuable : ce tag précis correspondra toujours au même code, peu importe les publications futures — indispensable pour diagnostiquer un problème en production ou revenir à une version antérieure connue
🤔 Testez-vous

Une image est déployée en production avec le tag latest. Un bogue apparaît après un déploiement récent, et vous voulez savoir précisément quel commit a produit l’image actuellement en production. Le tag latest vous permet-il de répondre à cette question ?

Réponse : non — latest est un tag mobile qui pointe vers la publication la plus récente, sans indiquer par lui-même quel commit l’a produite. Seul un tag immuable (comme le SHA du commit) permet de retrouver avec certitude le code source exact correspondant à une image donnée; c’est pourquoi on publie toujours les deux : latest pour la commodité, le SHA pour la traçabilité.

2️⃣ Créer une publication GitHub (Release) automatiquement

Une Release GitHub est différente d’une image publiée sur un registre : c’est une page dédiée du dépôt (onglet Releases) qui regroupe un tag Git, des notes de version, et éventuellement des fichiers joints (ex. le .jar compilé) — un point de référence lisible par des humains, utile même si vous ne distribuez pas d’image Docker.

Déclencheur : un tag Git plutôt qu’un push sur main

Contrairement aux jobs vus jusqu’ici (déclenchés à chaque push/pull_request), une Release ne doit se créer que ponctuellement, lorsqu’une version est prête à être publiée — on déclenche donc ce workflow sur la création d’un tag suivant une convention (ex. v1.2.3) :

on:
  push:
    tags:
      - 'v*'          # ex. v1.0.0, v1.2.3 — mais pas un push ordinaire sur main
# Créer et pousser un tag depuis votre poste pour déclencher ce workflow
git tag v1.0.0
git push origin v1.0.0

💡 Ce v* suit la convention du Versionnage sémantique (MAJEUR.MINEUR.CORRECTIF), que nous reverrons plus en détail une prochaine semaine — il suffit pour l’instant de retenir qu’un tag vX.Y.Z marque une version précise et volontaire du projet, distincte des commits ordinaires sur main.

Un job qui construit, publie la Release, et y attache le .jar

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write                 # requis pour que le workflow puisse créer une Release
    steps:
      - uses: actions/checkout@v5

      - name: Set up JDK 25
        uses: actions/setup-java@v5
        with:
          java-version: '25'
          distribution: 'temurin'
          cache: maven

      - name: Build
        run: ./mvnw -B clean package -DskipTests

      - name: Créer la Release et y attacher le .jar
        uses: softprops/action-gh-release@v2
        with:
          files: target/*.jar
          generate_release_notes: true    # génère automatiquement les notes à partir des PR/commits fusionnés
Élément Rôle
permissions: contents: write Sans cette permission explicite, le jeton GITHUB_TOKEN par défaut n’a pas le droit de créer une Release
softprops/action-gh-release Action tierce très utilisée (hors actions/* officiel) qui crée la Release correspondant au tag ayant déclenché le workflow
files: target/*.jar Joint le .jar compilé comme fichier téléchargeable directement depuis la page de la Release
generate_release_notes: true Génère automatiquement une liste des changements (basée sur les PR fusionnées depuis la Release précédente), sans rédaction manuelle

💡 Rien n’empêche de combiner les deux dans un même déclencheur par tag : un job qui publie l’image Docker avec le tag v1.2.3 (en plus du SHA et de latest — voir la section précédente) et un job qui crée la Release GitHub correspondante avec le .jar en pièce jointe — les deux pointent alors vers la même version exacte du projet, sous deux formes différentes (image exécutable vs archive téléchargeable avec notes de version).

🤔 Testez-vous

Votre équipe veut qu’une Release ne soit créée que pour des versions « officielles », jamais à chaque push sur main. Quel élément du workflow garantit ce comportement, et que se passe-t-il si quelqu’un pousse un commit ordinaire sur main sans créer de tag ?

Réponse : le déclencheur on: push: tags: ['v*'] garantit ce comportement — le workflow ne s’exécute que lorsqu’un tag correspondant au motif v* est poussé, jamais sur un push ordinaire de commits vers main. Un commit poussé sans tag ne déclenche donc aucune exécution de ce workflow, peu importe son contenu.
