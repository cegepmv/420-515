D'autres standards et outils de versionnage

SemVer est répandu, mais ce n’est ni le seul, ni toujours le mieux adapté. Voici deux autres standards réels, ainsi qu’un outil qui automatise l’application de SemVer.

1️⃣ CalVer : versionner par date plutôt que par signification

« CalVer est une convention de versionnage basée sur le calendrier de publication de votre projet […]. Cette approche basée sur le temps s’appelle le Versionnage Calendaire, ou CalVer en abrégé. » — calver.org

Contrairement à SemVer, où chaque segment a une signification précise (compatibilité), CalVer encode simplement la date de publication. Des projets réels, cités par calver.org, illustrent différents découpages :

Format Exemple réel Projet
YY.0M (année courte . mois) 26.04 Ubuntu
YYYY.MINOR (année . numéro séquentiel) 2026.2 JetBrains, Kali Linux
YYYY.0M.0D (année . mois . jour) 2026.08.19 yt-dlp

💡 CalVer convient bien à des projets publiés à un rythme régulier et prévisible (ex. deux fois par année pour Ubuntu), où la date de sortie est elle-même une information utile pour l’utilisateur. Il convient moins bien à une API dont la compatibilité doit être communiquée explicitement à chaque changement — ce que SemVer fait par construction, mais pas CalVer.

2️⃣ PEP 440 : le standard de versionnage de l’écosystème Python

Python a son propre standard de version, distinct de SemVer, défini par la Python Enhancement Proposal 440 :

« Les identifiants de version publique canoniques DOIVENT être conformes au schéma suivant : [N!]N(.N)*[{a|b|rc}N][.postN][.devN] » — PEP 440, Version scheme

Ce format ajoute des segments que SemVer n’a pas : un epoch (N!, rarement utilisé, pour réordonner un schéma de version historiquement incohérent), ainsi que des suffixes .postN (publication corrective après coup, ex. correction de la documentation seulement) et .devN (version de développement). Un paquet Python comme 2.1.0rc1 ou 3.0.0.post1 est donc valide selon PEP 440, mais ne correspond pas exactement à la grammaire de SemVer (voir SemVer).

3️⃣ Conventional Commits : automatiser le choix MAJEUR/MINEUR/CORRECTIF

Conventional Commits est une convention de messages de commit, conçue spécifiquement pour s’articuler avec SemVer :

« La spécification Conventional Commits est une convention légère par-dessus les messages de commit […] elle s’articule avec SemVer, en décrivant les fonctionnalités, corrections et changements cassants dans les messages de commit. » — conventionalcommits.org

Préfixe du commit Correspond à (SemVer)
fix: ... CORRECTIF (règle 6)
feat: ... MINEUR (règle 7)
feat!: ... ou pied de page BREAKING CHANGE: ... MAJEUR (règle 8)

Exemples réels, tirés de la spécification

La spécification elle-même fournit ces exemples de messages de commit valides :

docs: correct spelling of CHANGELOG

Aucun impact SemVer — docs n’est pas un type reconnu par la correspondance par défaut. — conventionalcommits.org, Examples

fix: prevent racing of requests

Introduce a request id and a reference to latest request. Dismiss
incoming responses other than from latest request.

CORRECTIF — préfixe fix:. — conventionalcommits.org, Examples

feat!: send an email to the customer when a product is shipped

MAJEUR — le ! après le type signale une rupture de compatibilité, même sans pied de page BREAKING CHANGE: explicite. — conventionalcommits.org, Examples

feat: allow provided config object to extend other configs

BREAKING CHANGE: `extends` key in config file is now used for extending other config files

MAJEUR — même en commençant par feat: (habituellement MINEUR), le pied de page BREAKING CHANGE: fait primer la rupture de compatibilité. — conventionalcommits.org, Examples

4️⃣ Automatiser l’application de SemVer : semantic-release

L’outil semantic-release relie directement Conventional Commits à SemVer et à une Release GitHub (voir Tags Git et publications (Releases) GitHub), sans intervention manuelle :

« semantic-release automatise l’ensemble du flux de publication d’un paquet, incluant : la détermination du prochain numéro de version, la génération des notes de version, et la publication du paquet […] en suivant strictement la spécification de Semantic Versioning. » — semantic-release.org, Introduction

Concrètement, dans un pipeline GitHub Actions, semantic-release lit l’historique des commits depuis la dernière version, détermine le type d’incrément SemVer à appliquer selon leurs préfixes, puis crée automatiquement le tag Git et la Release GitHub correspondants — remplaçant les étapes manuelles git tag / git push origin <tag> vues dans SemVer.

Exemple : correspondance officielle commit → type de release

Le dépôt officiel de l’outil illustre cette correspondance avec ces exemples précis :

Message de commit Type de release
fix(pencil): stop graphite breaking when too much pressure applied CORRECTIF (Fix Release)
feat(pencil): add 'graphiteWidth' option MINEUR (Feature Release)
perf(pencil): remove graphiteWidth option
pied de page BREAKING CHANGE: ...		 MAJEUR (Breaking Release)

— GitHub, semantic-release/semantic-release, README

Exemple : workflow GitHub Actions minimal

La documentation officielle propose ce point de départ pour exécuter semantic-release après la réussite des tests :

# .github/workflows/release.yml
name: Release

on:
  push:
    branches:
      - main

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write      # pour publier une Release GitHub
      issues: write        # pour commenter les issues concernées par la release
      pull-requests: write # pour commenter les PR concernées par la release

    steps:
      - name: Checkout repository
        uses: actions/checkout@v5

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 'lts/*'

      - name: Install dependencies
        run: npm ci

      - name: Release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: npx semantic-release

— semantic-release.org, GitHub Actions

Élément Rôle
on: push: branches: [main] Exécute semantic-release à chaque commit fusionné sur main — c’est l’outil, pas le déclencheur, qui décide s’il y a une nouvelle version à publier
permissions: contents: write Requis pour que semantic-release puisse créer le tag Git et la Release GitHub
npx semantic-release Analyse les commits depuis le dernier tag, détermine le type d’incrément (voir le tableau ci-dessus), puis publie

💡 Ce workflow n’utilise jamais git tag ni git push origin <tag> manuellement — semantic-release s’en charge entièrement, à condition que les commits respectent Conventional Commits (section 3️⃣).

🤔 Testez-vous

Un projet utilise semantic-release avec Conventional Commits. Les trois derniers commits depuis la dernière version publiée sont : fix: corrige une fuite mémoire, feat: ajoute un filtre de recherche, docs: corrige une faute dans le README. Quel type d’incrément SemVer semantic-release choisira-t-il ?

Réponse : MINEUR. Le commit feat: correspond à la règle 7 de SemVer (fonctionnalité rétrocompatible ajoutée) et prime sur fix: (CORRECTIF). docs: n’est pas un type reconnu par la correspondance SemVer par défaut et n’a aucun effet sur le choix de version. Aucun commit ne contient BREAKING CHANGE: ni !, donc pas d’incrément MAJEUR.
